# JetBrains v2: workflow parity and acceptance evidence

The native plugin can drive a real v2 session. That proves considerably more than a successful plugin build, but less than parity with either the pinned native plugin or the pinned VS Code extension. In particular, a session restored by a Kotlin adapter is not a session restored in a reconnected JetBrains Client. A command shipped by VS Code is not necessarily a command the native plugin has ever offered.

## What was compared

- **v1 VS Code:** [`packages/kilo-vscode` at `fb7e96eda54`](https://github.com/Kilo-Org/kilocode/tree/fb7e96eda5409517a05948b9efaf01c53997bf6e/packages/kilo-vscode), the `pins.v1Target` in [features.json](../progress/features.json). Source of the command inventory: `package.json` → `contributes.commands`, plus `src/extension.ts`, `services/code-actions`, `services/autocomplete` and `agent-manager`. The manifest has **73** entries: 6 sidebar-title aliases, 32 `agentManager.*`, 4 `autocomplete.*`, 31 others. Settings, tools and buttons that have no command ID are accounted for separately below.
- **v1 JetBrains:** [`packages/kilo-jetbrains` at the same pin](https://github.com/Kilo-Org/kilocode/tree/fb7e96eda5409517a05948b9efaf01c53997bf6e/packages/kilo-jetbrains), git tree `a7d84ad5d570`. The native baseline is its split module descriptors, Swing controllers and backend callers, **not** the VS Code extension running inside JetBrains. For example, `KiloSessionRpcApiImpl` actually delegates share, unshare, list cloud history and import; `KiloBackendTelemetry` actually posts capture/consent to v1. Conversely, there was prompt completion, but no source-editor FIM provider in that descriptor.
- **v2 JetBrains:** [native package](../../packages/kilo-jetbrains), audited 2026-11-19 on the port based on `c55da21722c`. Compare the [frontend registrations](../../packages/kilo-jetbrains/frontend/src/main/resources/kilo.jetbrains.v2.frontend.xml), [backend registrations](../../packages/kilo-jetbrains/backend/src/main/resources/kilo.jetbrains.v2.backend.xml), backend `rpc/`, `session/`, `workspace/`, and `editor/`. Build-time Kotlin operation generation uses the assembled checkout contract; the installed plugin runs the exact CLI version in [package.json](../../packages/kilo-jetbrains/package.json) (audit pin `0.0.0-v2-194`). A working feature in checkout `bun dev` does not retroactively add it to that release.

**Reading the tables:** *live* means the stated path was exercised against a real v2 process; *component* means a focused automated test, possibly with a fake RPC/model; *wired* means an actual caller/handler was found, without a recorded end-to-end pass for that workflow; *missing* means no equivalent implementation, or an unconditional unavailable response. The pinned columns describe code, not a historical acceptance run. See the real-IDE evidence separately.

## Workflows that a command count misses

| Surface | Evidence on the pin | v2 JetBrains: outcome, boundary, and next action |
|---|---|---|
| Start/recover, CLI ownership | Native backend started and checked a platform CLI; frontend did not own its HTTP secret. | Live (macOS arm64): generated `V2Client`, `CliRuntime` and a fresh checkout CLI, downloaded exact npm pin and optional bundled host archive; authenticated `server.info`, `session.create`, changed PID on restart and exit on stdin EOF. Wrong server/version/auth, redirects, packed assets and restart deserve their own tests; no other OS is established by six archive hashes. |
| Chat, persisted history, approvals, question forms | Both clients prompt, stream, resume, fork, stop, inspect diffs; pinned native has permissions, question cards, revert/redo, model/agent/variant, `/` and `@` completion. | Live adapter: real v2 `session.prompt`, SSE delta, pending edit, allow once, changed file and persisted messages; reconnect reads projections (`SessionFeed`, `SessionRequests`). Component: paginated rehydrate/removal, stable part identities, typed form answer. Wired but not thereby IDE-tested: retry/abort, queue cancel, revert/redo, multi-project selection, image/mention attachment, fork/truncation, stop/promote a **running** subagent. |
| Board and background agents vs Agent Manager automation | Native displays the board, child sessions and jobs. VS Code also answers model-driven `agent_manager` requests (v1 `agent-manager/orchestration-bridge.ts`). | Native board owner/empty jobs read live; controller/view and job RPCs exist. `CliCommand.kt` strips `KILO_AGENT_MANAGER_HOST`; [`kilo-plugin/src/agent-manager`](../../packages/kilo-plugin/src/agent-manager/index.ts) registers the orchestration tool only with a host. Native manager **UI** does not implement the tool's list/start/prompt/stop/move/answer bridge. Implement/verify the request owner, reconnect, rejection and response routing before advertising that capability. |
| Worktrees, runs and diffs | Native project/worktree RPCs cover VFS open, branch/local comparison, PR/history, isolated terminals and run configurations. Test in a disposable repo: staged+unstaged+untracked move, dirty failure, imported branch preservation, setup/run cwd, external PR link, diff target, stop and reopen. Native display-name rename is **not** `git branch -m`. |
| FIM vs prompt completion and naming | VS Code offers editor FIM, configurable source provider, Next Edit, and optional chat autocomplete. Native `KiloPromptCompletionProvider` offers file/command lookup; prompt enhancement is separate. | Real local IDE: one cold `Kilo.GenerateInlineCompletion` call sent prefix `const fixture = ` and empty suffix; the fixture returned `42` and IntelliJ rendered an inline inlay. Branch suggestion before a move with a source session is not VS Code's background rename of an unnamed plugin-owned branch after early prompts. | Accounts, settings, MCP, marketplace, migration | Both clients have profile/provider/config settings. Native includes device auth, organizations, skills/commands/rules, MCP OAuth, marketplace and opt-in **JetBrains v5** import. ## Known unavailable paths: what to fix before claiming support

| User-visible risk | How to verify or close it |
|---|---|
| **Public share vs private sync.** `KiloSessionRpcApiImpl.share/unshare` unconditionally throw; no native public link/revoke/viewer on the CLI pin. Earlier `cloudSessions/importCloudSession` throws have been replaced in source by `KiloCloudSessions`: `kilocode.cloud-history` capabilities/list/download → `experimental.session.import`. The published pin has no native reader RPC or Git-remote filter. | Gate Share/Stop/Copy, cloud-history list/import and repository filtering separately. Verify signed-out/old-pin/retry and restored-session UX; no success toast, never substitute a private blob URL or v1 transcript. Test paginated owner-private list/import on a released reader; individual public issuance, restoration, revocation and viewer require separate cloud/server work. [#15306](https://github.com/Kilo-Org/kilocode/issues/15306), [#15313](https://github.com/Kilo-Org/kilocode/issues/15313). |
| **Automatic/manual cleanup.** The initial constant `supported=false`/throw was replaced in source: `RetentionEndpoint` checks `kilocode.retention/status`, exact vetted pin and `kilocode.handshake/get` before allowing `run`. No production version is certified; cleanup is **unavailable on -194**. | Keep policy/global ownership and runtime gating. Don't simulate machine-wide safety with client enumeration/deletion or transiently enable the saved policy. Before certifying a release, exercise enabled/disabled policy, concurrent activity, skipped tree and failure/result. Server dependency: [#16159](https://github.com/Kilo-Org/kilocode/pull/16159). |
| **Production telemetry.** The native constructor of `KiloTelemetryService` passes `capture=null`; `send()` returns, including in sandbox. `CliCommand` now forces the child's telemetry level off. The native pin had a real backend capture and consent path. | This is intentional pending an approved sink/consent policy, but still **missing**, not tested delivery. Do not send arbitrary event maps. Bind a consent-aware server sink on a compatible release, verify opt-out before the first event and allowlist metadata. [#15303](https://github.com/Kilo-Org/kilocode/issues/15303), [#16160](https://github.com/Kilo-Org/kilocode/pull/16160). |
| **Settings that save but have no effect.** The port removed pinned global subagent model/variant and prune controls: the former have no runtime consumer and `workspacePatch` refuses `compaction.prune`. Per-agent model and compaction `auto`/`buffer` remain. The launcher also removed its trailing inline `edit:* ask`, which overrode saved project/global decisions. | Verify the latest source in an installed build. Check the **effective** provider/model/agent and permission result as well as read-back JSON: default, saved top-level edit deny, saved allow and per-agent override. Replace stale `bash`/`task` settings and permission-card matching with canonical `shell`/`subagent`; keep aliases for old imported history. Check sensitive/interactive-only requests still display a manual card. |
| **Presentation can miss a real operation.** Native renderers originated on the v1 tool names `bash` and `task`; v2 sends `shell` and `subagent`. A generic tool card can display output while dropping specialized shell UI, child-session links or live state. | Route canonical IDs through native `ToolView`, `SessionModel`/`SessionController` child handling and tests. Exercise an actual shell and a running child, open it, stop/promote, then reconnect. An empty `backgroundJobs` response or a unit test feeding `task` cannot pass this scenario. |

Other apparent stubs are intentional limits, not bugs: read-only synthetic VFS files reject stream writes, read-only child editors disable mutations, `SessionManager` capability defaults hide actions on surfaces that cannot handle them, and failed worktree/`gh` polling reports *unavailable* rather than a clean tree. Preserve those distinctions.

## What “excluded at cutover” means

[Plan, Out of scope](../plan.md#out-of-scope) says **not carried, or post-cutover/non-gating unless explicitly made a gate**; [#15321](https://github.com/Kilo-Org/kilocode/issues/15321) records later ship/drop/re-scope decisions. That is a scheduling decision, not evidence of parity, a ban on subsequent ports, or a reason to ship visible dead controls.

- The explicit list is voice/speech-to-text, image generation, **team and incremental** sharing, legacy TUI extras, default-off **experimental** v1 features, KiloClaw, upstream Desktop/web/hosted platform and upstream contributor config. VS Code's pinned experimental browser flag was `false`; native notebook tools are identified as default-off in the [wire migration note](v1-v2-client-breaking-changes.md). Some were implemented later in v2 VS Code; this does not make them available in JetBrains. A personal preference being initially off is not by itself an experimental exclusion.
- **Individual** share/unshare/fork-from-share/viewer, memory/indexing, relay, and editor services have their own M2/M3 epics. Default-on experimental background subagents/board are expressly in scope. The JetBrains epic [#15316](https://github.com/Kilo-Org/kilocode/issues/15316) proposes that FIM does not gate its native port because native v1 had no FIM. That does not make FIM unnecessary for **VS Code** parity, or excuse incomplete prompt completion/generation. Conversely, Next Edit/Mercury has a separate retirement decision.
- A VS Code-specific integration (Chart.js, in-chat search, Agent Manager shortcuts) absent from both native versions is a delta against VS Code, not a newly broken native feature. Native share, cloud history, cleanup or telemetry behaving worse than the native pin is a native regression/dependency even if the rest of chat works. Neither comparison alone closes G3 or constitutes a release/rollback decision.
