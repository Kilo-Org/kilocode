### 2. Orchestration bridge `stats()`/`prs()` silently drop the request directory — background-project overviews lose git/PR annotations

- **Chain:** orchestration request routed by directory (`orchestration-bridge.ts` `admit`/`execute`, `origin.directory`) → directory-aware `root`/`state`/`ready`/`push`/`managed`/`close` resolvers (`orchestration-setup.ts:30-61`, each resolves `contexts.byDirectory(dir)`) → `overview({ state, root, stats, prs })` (`orchestration-domain.ts:271-275`) → `worktreeSummaries` looks stats up by `worktreeId` (`orchestration-domain.ts:236,243-244`).
- **Weak link:** the `Options` interface threads `directory?` through `stats(directory?)` and `prs(directory?)` (`orchestration-bridge.ts:46-47`), but the implementations discard it: `stats: () => deps.getStats()`, `prs: () => deps.getPrs()` (`orchestration-setup.ts:42-43`), and `getStats` is the ACTIVE project's singleton poller snapshot (`AgentManagerProvider.ts:266-267`). Per-project pollers for expanded background projects exist (`project/pollers.ts:60-80,149-188`) but their snapshots are never consulted here. An orchestration `overview` aimed at a background project's directory therefore pairs that project's state with the active project's stats/PR map.
- **Impact assessment:** graceful, not corrupting — worktree IDs are `wt-<ms>-<globalCounter>` (`WorktreeStateManager.ts:113-115`), collision-proof across projects within a process, so `stats.get(worktree.id)` simply misses and the `git`/`pullRequest` annotations are omitted from the response. The IDs and session payloads remain correct.
- **Human verification:** confirm the graceful-degradation reading and decide whether background-project overviews should surface annotations; if yes, thread the per-project poller snapshots into `createOrchestrationBridge`'s `stats`/`prs`. Reproduce: expand two projects in Agent Manager, issue an orchestration overview scoped to the background project's directory, observe missing ahead/behind and PR data while the active project's overview shows them.

### 4. `ensureGitignore` does not catch `EROFS` — config load dies when `KILO_CONFIG_DIR` points into a read-only filesystem

- **Chain:** `KILO_CONFIG_DIR` env → `loadInstanceState` directory loop (`config/config.ts:707-749`) → `ensureGitignore(dir)` → `fs.ensureDir(dir)` (`config.ts:434-441`) → `mkdir`.
- **Broken link:** the `kilocode_change` catch covers only `PermissionDenied` and `NotFound` (`config.ts:436-439`). An `EROFS` surfaces from effect's FileSystem as a `PlatformError` with reason `"Unknown"` (observed: `_tag: "Unknown", method: "makeDirectory"`), escapes the catch, hits `.pipe(Effect.orDie)` at `config.ts:749`, and defects the whole config load. Observed empirically: the delta's new test `test/kilocode/tool/shell-env.test.ts` sets `KILO_CONFIG_DIR=/secret/config` and fails in this machine's agent sandbox (`EROFS: read-only file system, mkdir '/secret'`), while on a normal host the same mkdir yields `EACCES` → `PermissionDenied` → caught → test proceeds. CI is therefore green and only EROFS environments trip it, but hardened/container environments with read-only roots are exactly where this would bite.
- **Human verification:** confirm whether `EROFS` should join the caught reasons in `ensureGitignore` (the dir is optional config state; failing closed on it aborts startup). Note the test's intent (credential scrub) is unaffected — it never reaches its assertion under EROFS because the defect happens during layer build, before tool execution.
