### 1. httpapi-pty live-websocket tests exceed bun's default 5 s ad-hoc timeout in this sandbox (low — flag: human verification)

- **What:** At `4bb1c2a45b`, `bun test ./test/server/httpapi-pty.test.ts` (default per-test timeout 5000ms) fails twice: `disposes PTY sessions with their legacy instance` (5098ms) and `serves PTY websocket output and input through Effect routes` (5400ms). Both are the file's only `effectIt.live` tests driving a real HTTP server + real websocket + real spawned PTY; the seven in-process `app().request` tests pass. With `--timeout 20000` the file goes **9 pass / 0 fail** (46.29s).
- **Attribution:** not the fix commit — the disposal/websocket code path is untouched by it (the commit's only runtime-source changes are `ensureGitignore` catch scope, the models-dev default URL, and kilo-vscode `GitOps` env scrubbing, none in the PTY path), and the same file passed at `b793883de6` in round 4's session. The failure shape is environment-boundary slowness: "disposes" spawns `sh -c "sleep 5"` and its teardown crosses the 5 s line exactly (5098ms) — child/PTY teardown under this session's sandbox (which also blocks outbound network and slows process operations) outruns bun's default timeout. CI does not run files this way: `script/test-runner.ts` passes `--timeout 60000` per test (default, line 77), and round 4's green run used a batch invocation.
- **Why flagged anyway:** round 4 ran the identical file green in an equally local batch, so something about this session's environment is slower; that is precisely the loaded-runner condition CI watchers care about. Per the review convention, flagged for a human to confirm CI stays green rather than asserted as a regression. No code change recommended.

## Limitations

- **Sandboxed local execution, not CI:** this session's agent sandbox blocks outbound network and measurably slows process/PTY teardown — it produced the two 5s-timeout httpapi-pty failures and plausibly contributes to the vcs-watcher flake. CI runs suites via `script/test-runner.ts` with a 60s per-test default, so neither shape is expected there; both are flagged for CI observation rather than asserted as regressions.
- **No same-session A/B run at `b793883de6`:** the read-only brief forbids checking out the old head, so New finding 1's attribution to environment rests on code-path inspection (the fix commit touches nothing in the PTY/disposal path), the exact 5s-boundary failure shape, and the 20s-timeout pass — not on a controlled re-run at the previous head.
- The kilo-vscode, kilo-ui, and kilo-jetbrains suites were not re-executed this round: the fix commit's only kilo-vscode change (`GitOps.ts`) has no covering suite, and no other delta file belongs to those packages; carried coverage claims were re-verified statically at the new head.
- The vcs-watcher parallel reproduction used a different 4-file mix than rounds 3–4 (per the brief, "a few parallel suites"); the failure signature is identical, so cross-round comparison is by shape, not identical load.
- Marker counting and upstream-attribution carry the standing caveat from rounds 1–4: a Kilo assertion written in fully generic terms inside a shared file is indistinguishable from upstream content. Mitigations unchanged: per-block attribution against upstream tag `a105350812`, removed-line and kilo-reference scans; every removed block in the full-PR sweep is attributed.
