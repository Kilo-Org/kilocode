## New findings (round 2)

### 1. `promptCacheKey` narrowed for `openai`-provider models using `@ai-sdk/openai-compatible` — needs human confirmation

- **Chain:** `sessionID` → `ProviderTransform.options()` → `promptCacheKey` in the request body → OpenAI prompt-cache affinity (cost/latency).
- **Changed link:** pre-merge base set `promptCacheKey` for **every** model whose `providerID === "openai"`, regardless of npm (`git show b135b4e10a:packages/opencode/src/provider/transform.ts`, the `setCacheKey !== false && (providerID === "openai" || npm === "@ai-sdk/xai" || setCacheKey)` block, base lines ~1443-1448). The merged tree narrows this to `(input.model.providerID === "openai" && input.model.api.npm !== "@ai-sdk/openai-compatible")` (`transform.ts:1566-1567`, marked `kilocode_change - retain cache keys for OpenAI providers using nonstandard SDK packages`). Every other base case is preserved at head: `@ai-sdk/openai`/`@ai-sdk/azure`/`@ai-sdk/xai`/`@ai-sdk/mistral`/`venice-ai-sdk-provider` are in the head's npm list (`transform.ts:1560-1571`), the base azure block and venice-provider block are subsumed by that list, and `setCacheKey === true` still forces the key.
- **Why it matters:** a user who overrode the built-in `openai` provider's npm to `@ai-sdk/openai-compatible` (e.g. an OpenAI-compatible proxy fronting real OpenAI models) had `promptCacheKey` set before the merge and silently loses it after — a cache-hit/cost regression only, no error. The narrowing looks deliberate (it mirrors upstream's exclusion and the marker wording), but it is a behavior change vs pre-merge Kilo introduced in the compat pass and preserved by the fix commits; round 1 did not flag it.
- **Human verification:** confirm the exclusion is intended. If Kilo's default/model-catalog config ever maps `openai`-provider models to `@ai-sdk/openai-compatible`, restore the broader condition; otherwise close as accepted.

### 2. Modal plugin fallback round-trips internal state through the silent `toPublicInfo` filter — low risk, for awareness

- **Chain:** internal `provider.models` → `toPublicInfo(provider)` (applies the `Schema.is(Model)` filter, `provider.ts:1456`) → `ModalPlugin.provider.models(provider, ctx)` → on discovery failure or missing credentials returns the **filtered** copy (`plugin/modal/modal.ts:14-21`) → hook merge stamps ids and **replaces** internal `provider.models` (`provider.ts:1455-1467`).
- **Observation:** the delta's preserve-on-failure fix (strictly better than the round-1 head, which returned `{}` and emptied the provider) means a transient discovery failure now permanently rewrites internal state to the filtered public copy. Any internally-stored model that fails `Schema.is(Model)` would be dropped from internal state, not just from API responses — amplifying finding (b) from "hidden in responses" to "lost from state" for the modal provider specifically.
- **Assessment:** no known Kilo or modal construction path produces a non-conforming model (round 1 and this round both checked), so the practical risk is low; it materializes only in combination with finding (b) actually tripping.
- **Human verification:** none required beyond finding (b)'s; if (b) is ever observed for the modal provider, note that a single failed discovery refresh makes the drop permanent until restart.

### 3. `ensureDir` lost upstream's "exists-but-not-a-directory" recheck — edge-case semantic narrowing

- **Chain:** session/storage writes → `FSUtil.ensureDir` (`packages/core/src/fs-util.ts:117-119`) → `ensureDirectory(fs, path)` (`packages/kilo-sandbox/src/filesystem.ts:15-22`) → `fs.makeDirectory(path, { recursive: true })` with `AlreadyExists` swallowed.
- **Changed link:** the delta removed the outer `Effect.catchIf(AlreadyExists → isDir recheck)` wrapper that the round-1 head had kept from upstream (`a105350812` still has it around `fs.makeDirectory`). Functionally the Bun-on-Windows EEXIST workaround survives because Kilo's `ensureDirectory` already catches `AlreadyExists` internally — so the removal is safe for the documented bug. The residual difference: upstream re-failed when the existing path was **not** a directory; Kilo's version treats any `AlreadyExists` as success, so `ensureDir` on a path that exists as a file now "succeeds" and the failure surfaces later at the write with a less obvious error.
- **Human verification:** confirm the narrowed semantics are acceptable (sandbox-confined writes would fail closed anyway). If not, add the `isDir` recheck inside `kilo-sandbox/src/filesystem.ts`'s `ensureDirectory` rather than at call sites.
