## New findings (round 3)

### 1. `privacy_mode` is settable at project scope via the overlay but only ever read from the global config

- **Chain:** schema `privacy_mode` (`packages/core/src/v1/config/config.ts:135-138`) → config-console overlay field list (`packages/opencode/src/kilocode/config/overlay.ts:91`) → overlay writer (`handlers/config-console.ts:72-146`, scope "global" | "project") → TUI reads `sync.data.globalConfig.privacy_mode` (`packages/tui/src/context/sync.tsx:95,625,792-829` via `GET /global/config` → `Config.getGlobal` → `loadGlobal`, which merges only `Global.Path.config` files, `config/config.ts:363-383`) → consumers: sidebar-footer blur (`kilocode/plugins/sidebar-footer.tsx:103-105,181,188`), `/profile` confirmation gate and `/privacy` toggle (`kilocode/kilo-commands.tsx:142-149,190-220`).
- **Broken link:** `overlay.ts` `fieldPaths` is scope-agnostic — `resolve()` builds fields for both scopes (`overlay.ts:197-216`), so a client can write `privacy_mode: true` into a *project* `kilo.json`. No reader ever looks there: the TUI reads only `globalConfig` (global files), and no other package reads `privacy_mode` at all (repo-wide grep: schema, SDK type, overlay, sidebar-footer, kilo-commands only). A project-scoped set silently does nothing — no blur, no confirmation gate, no warning.
- **Context:** the feature landed in this delta (new `/privacy` command, footer blur, overlay entry). The in-tree writer (`/privacy`, `kilo-commands.tsx:201-204`) hardcodes `scope: "global"`, so the gap only trips via the generic overlay surface (config-console UI / direct API).
- **Human verification:** confirm the intended semantics. If privacy_mode is meant to be global-only, filter it out of project-scope targets in `overlay.ts`; if project scope should work, read the merged config (`sync.data.config.privacy_mode`) instead of `globalConfig` in the two TUI consumers. Reproduce: set `privacy_mode: true` in a project `kilo.json`, open the TUI, observe the balance is not blurred and `/profile` shows without confirmation.

### 2. Agent Manager git fetch fails closed when the extension host env carries `GIT_CONFIG_COUNT` / `SSH_ASKPASS` / `GIT_ASKPASS` — silent stale-ref fallback

- **Chain:** Agent Manager worktree creation / branch prefetch → `WorktreeManager.resolveStartPoint` (`packages/kilo-vscode/src/agent-manager/WorktreeManager.ts:756-839`) and `prefetchBase` (`WorktreeManager.ts:155-159`, called from `worktree-importer.ts:37`) → `refreshBase` (`WorktreeManager.ts:839-855`) → `simpleGit(root, { unsafe: { allowUnsafeSshCommand: isKiloOwnedSshCommand(env) } }).env(nonInteractiveEnv()).fetch(...)`.
- **Weak link:** `nonInteractiveEnv()` (`GitOps.ts:77-86`) spreads the entire `process.env` into simple-git's `.env()`. simple-git hard-fails (`Use of "GIT_CONFIG_COUNT" is not permitted without enabling allowUnsafeConfigEnvCount`, similarly `SSH_ASKPASS`/`GIT_ASKPASS` without `allowUnsafeAskPass`) when those variables are present, because only `allowUnsafeSshCommand` is (conditionally) enabled. The throw is caught in `resolveStartPoint`, which then returns the stale local tracking ref with a `warning` — worktree creation proceeds off a potentially outdated base, and the only signal is a log line.
- **Evidence (reproduced):** a standalone script building a seed→bare→clone repo and calling `resolveStartPoint("main")` at this head returned `{ source: "local-tracking", warning: "Used stale remote tracking branch (fetch failed)" }` under this machine's agent shell (which exports `GIT_CONFIG_COUNT`, `SSH_ASKPASS`, `GIT_ASKPASS`); with those three unset it returns `{ source: "remote" }`. The same env contamination makes `tests/unit/worktree-manager.test.ts` "resolveStartPoint > returns bare branch + remote when remote exists" fail (`expected "remote", received "local-tracking"`); the full kilo-vscode unit suite passes 3785/3785 with a sanitized env (see Test outputs).
- **Provenance:** the `.env(nonInteractiveEnv())` call shape predates the delta (the delta refactored the identical call into `refreshBase` unchanged), so this is not a merge regression — but the delta's perf work (`prefetchBase`, cached preflights, more frequent background stats/fetch in `GitStatsPoller.ts`/`git-stats-snapshot.ts`) increases how much Agent Manager behavior rides on these background fetches succeeding.
- **Human verification:** decide whether `nonInteractiveEnv()` should strip or neutralize `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_*`/`GIT_CONFIG_VALUE_*`/`SSH_ASKPASS`/`GIT_ASKPASS` (or pass the matching `unsafe` flags — it already computes a fixed non-interactive SSH command, so askpass tools are never usable in this path anyway). Note VS Code itself sets `GIT_ASKPASS` for processes it spawns in some configurations, so this is reachable by real users, not just test harnesses.

### 3. Forked task-child sessions created by `remapChildren` lose platform telemetry attribution

- **Chain:** session fork (`packages/opencode/src/session/session.ts:841-916`) → new `KiloSession.remapChildren` call (`session.ts:909-915`, added by this delta) → `copy()` (`kilocode/session/fork.ts:82-125`) creates each forked child session via `ops.create({ parentID: fork.id, title, agent, model, metadata, permission, workspaceID })` → `createNext` → `KiloSession.register({ id, parentID, platform: input.platform })` (`session.ts:660`).
- **Gap:** `copy()` never passes `platform`. `register` inherits via `resolvePlatform(parentID)` when `platform` is undefined (`kilocode/session/index.ts:72-79`), but a fork is a root session (no `parentID`) and the fork's own `createNext` call (`session.ts:866-877`) also passes no `platform` — so `resolvePlatform(fork.id)` is `undefined`, and every remapped child of a fork resolves to `undefined` → downstream consumers fall back to `process.env["KILO_PLATFORM"]` (`kilocode/session/index.ts:126`, `kilo-sessions/kilo-sessions.ts:701,1330`).
- **Delta-relevant change:** pre-delta, forked transcripts kept the *original* child session IDs in task parts, and those originals carried their own registration (platform inherited from the original parent). Post-delta, forked parts point at the new copies, which have no attribution. Scope is narrow (telemetry feature tagging on forked subagent sessions only) and the fork-loses-platform behavior itself predates the delta.
- **Human verification:** confirm acceptable, or thread `platform: KiloSession.resolvePlatform(input.source.id)` (and the fork's own `original`) through `copy()`/fork's `createNext` call. Observe via telemetry: fork a session that ran task subagents under `KILO_PLATFORM=vscode`, resume a forked task, and check the child session's platform attribution.
