# JetBrains preview: canary and rollback

The preview is a **separate plugin, not an update to the stable plugin**. Install it from disk or from the preview listing/channel. In **Settings → Plugins → Installed**, disable **Kilo Code** before enabling **Kilo Code (v2 preview)**, then restart the IDE. In Remote Development, apply the switch to **both host and client**, stop the previous remote IDE, and reconnect. Never merge the contents of two plugin ZIPs.

| | Stable | Preview |
|---|---|---|
| Plugin ID | `ai.kilocode.jetbrains` | `ai.kilocode.jetbrains.v2` |
| Install directory / content module prefix | `kilo.jetbrains` | `kilo.jetbrains.v2` |
| Project runtime config / managed worktrees | `kilo.json[c]`, `.kilo/` | `kilo2.json[c]`, `.kilo2/` |
| Native diagnostic log (per IDE process) | `kilo.log` | `kilo2.log` |

The preview declares stable incompatible: the action IDs, tool window and split RPCs are not designed to be active twice. The platform may refuse to enable the preview until stable is disabled. Do not depend on a particular plugin winning when both are enabled. Platform-owned settings such as layout and keymaps are common to the IDE profile. Use separate profiles to keep those customizations independent too.

The preview keeps native `kilo2.*` preferences and `kilo2AutocompleteSettings.xml` / `kilo2LogSettings.xml` separately. The backend keeps native model and migration state in the IDE config directory's `kilo2/`, and the CLI installation under `<IDE system>/kilo2/cli/<pin>/<platform>/`. The installed CLI uses its runtime's `kilo2` config, data, cache and state directories; the development launcher uses an isolated `KILO_V2_PROFILE`. Legacy import is optional: decline/skip for a clean trial. An explicit import reads source data and stages a separate copy. Do not copy or rename a session database, credentials or worktree directory between versions.

## Build the candidate

1. From the checkout root, `bun install`. From `packages/kilo-jetbrains`, run `bun run typecheck` and `./gradlew test`.
2. Set the **plugin** version via `-Pkilo.version=<version>` (default `kilo.jetbrains.version` in `gradle.properties`). The separate `package.json` version pins the **CLI**. When changing the CLI pin, run `bun run pin:cli`; review `backend/src/main/resources/kilo-v2-cli.properties`, including all six npm SHA-512 integrity values. Keep `kilo.cli.pinned=true` for production builds.
3. Use `script/build-version.sh <version>` for the signed, verified ZIP. This runs `buildPlugin`, `signPlugin`, `verifyPluginSignature` and `verifyPlugin`; signing uses `JETBRAINS_CERTIFICATE_CHAIN` / `JETBRAINS_PRIVATE_KEY` (or their `_FILE` variants) and `JETBRAINS_PRIVATE_KEY_PASSWORD`. For a local unsigned candidate, `bun run build:production` builds under `build/distributions/`. An offline bundle uses `./gradlew buildPlugin -Pproduction=true -Pkilo.cli.bundled=true` and needs a separate smoke run without registry access.
4. Record ZIP SHA-256, plugin version/ID, CLI pin, IDE build and OS/CPU. Inspect the installable ZIP: exactly one `kilo.jetbrains.v2/` root; each of the three module JARs under `lib/modules/`; `META-INF/plugin.xml` with the preview ID and `<incompatible-with>ai.kilocode.jetbrains</incompatible-with>`. Reject artifacts with the old install root. Keep the previous signed preview ZIP and a verified signed stable ZIP available for rollback.

## Canary in disposable profiles

Use a disposable OS account/VM or container with a graphical desktop and its own home and IDE configuration. **Never import a developer's IDE settings, license files, tokens or Kilo directories.** For split mode, isolate both processes. Use an empty test repo, not the checkout. In a shared OS account, explicitly isolate `HOME`, JVM `user.home`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME` and all four `idea.{config,system,plugins,log}.path` values; turn off Settings Sync and shell-environment loading. Use only fixture identity and data. Do not set `KILO_USE_RELEASE_CONFIG`.

1. **Baseline:** install stable in the empty profile. Change a native preference (e.g. auto-approve), create a stable fixture session/worktree and quit. Record stable settings, session title/ID, worktree path, and hashes of fixture-owned stable config/data files after shutdown. Keep the ZIP and a copy of this *temporary* profile. Do not hash entire shared IntelliJ option files to compare settings: compare the stable keys inside them.
2. **Switch and exercise:** disable stable, install the candidate from disk, enable preview and restart. In Core Info verify the expected CLI pin. Verify only one Kilo action set/tool window, no duplicate registrations in `idea.log`, that preview did not inherit stable auto-approve, and no stable session/worktree appears. Create a preview session, change a native preference, approve a fixture edit, then stop an in-flight prompt. Wait for idle; check the edit stopped and the IDE remains responsive. Restart and reopen the preview session. Inspect both sides' logs in split mode.
3. **Isolation:** verify only preview-owned project and data paths changed. In particular, inspect stable's session/worktree and config fixtures, native preference keys, log rotations and any legacy migration inputs. Record the PID of the preview's `serve --port 0 --stdio` child. Disable preview/restart the backend and verify that PID exited; closing only a remote frontend may leave a running host. Never kill another IDE's CLI by process name.
4. **Round trip:** enable stable again, restart both sides as applicable, and open the original session/worktree. The original preference, transcripts, config and worktree files must still be intact; preview history must not appear. Switch once more to the preview and reopen its independent session. If narrowing a regression within the preview, install the previously verified preview ZIP with the preview disabled; use a copy of the fixture profile when testing a downgrade across database schema changes.
5. **Repeat:** run this with the installed release artifact on local and split IDEs; cover the online downloader and offline bundle. Separately run the repeatable UI scenario from [script/self-test/README.md](script/self-test/README.md). That harness exercises a checkout CLI, so a green result does not verify the binary shipped or downloaded by the release artifact.

**Promotion gate:** start with the preview EAP channel/internal cohort. Record the checksums, actual enabled plugin IDs, stable → preview → stable → preview observations, child exit, fixture checks and failures for each IDE/OS lane. Keep telemetry evidence free of credentials and session content; IDE diagnostic logs are not a success metric. Hold promotion on data changes in stable, a duplicate registration, CLI mismatch, an orphan after shutdown, or a blocked local/split lane. A build or signature check alone does not satisfy the canary.

**Rollback:** stop distribution of the failing candidate on the preview channel. Disable preview, restart, enable the existing stable plugin (or install the verified signed stable ZIP) and restart. In Remote Development, switch both host and client and reconnect. Leave both versions' state in place; remove **only** the preview plugin if necessary. Do not delete `.kilo`, `.kilo2`, credential stores, CLI databases, or worktrees as part of rollback. A source edit made during a session is an ordinary working-tree edit and is not undone by switching plugins.
